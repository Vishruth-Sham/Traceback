## Scope and visual direction

Build a PC browser UI for one user/admin. Follow the existing mockups' visual direction and screen layouts where they match current decisions. Avoid another navigation redesign. Use a proposed Next.js frontend against the local REST API; no direct database calls from the browser.

The original standalone HTML remains unchanged. Replace its mock controls and status labels with real interactions during implementation. No mobile layout work is required in this version; desktop window resizing, scrolling, keyboard access, and browser zoom still need to work.

## Manual control is mandatory

Every implemented content type must be usable directly through the UI, even when AI processing is disabled and no MCP client is connected.

- Show an obvious Add action in Tasks, every category including Other, and project pages. Context can prefill a destination; the user can change it.
- Let users edit titles, content, dates, and all supported type-specific fields, including values originally generated by AI.
- Provide Move to, project/entity link and unlink, attachment add/remove, complete/reopen where applicable, and archive actions from item details. Search results and linked items open those same editable details.
- Inbox supports manually creating a note/task from a capture or adding it to an existing item; users do not need to retry AI just to organize saved content.
- Archive provides restore and confirmed permanent deletion. Original capture content stays preserved; users can add versioned corrections to derived transcripts/context without losing the original.
- User changes save directly and update every appearance of the same item. Pending automated work must not silently reverse manual edits or routing.

Keep the seeded top-level categories as agreed. Manual control here applies to content and its organization. When a new tracking feature becomes available, its manual entry/edit controls must be included in that increment.

## Tasks

Keep one list with Open and Completed filters. Do not add Today, a planned date, a calendar dashboard, or mandatory categorization.

Each row: real checkbox, title, quiet optional category/project label, and due date/time if present. Open tasks sort by due date: overdue, upcoming, then undated. Make overdue deadlines legible with text as well as color. Completed sorts by completion time, newest first.

An inline “Add a task…” input accepts free-form natural language, not only a pre-structured title. For example, “Email Sarah Friday afternoon about the apartment move” is saved immediately as the original task-entry capture, then the local LLM parses it into a structured task proposal: title, optional deadline/timezone, category, project/folder association, and notes. The validated backend stores the resulting canonical task and preserves the original text as provenance. The user can review and edit every parsed field; ambiguous or failed parsing must leave the saved input available for manual task creation rather than losing it. Undesignated tasks live in Inbox for classification but also appear in Tasks; this is one object in two queries, not a duplicate.

Implemented (2026-09-14) as `frontend/src/components/TaskQuickAdd.tsx` on the Tasks page: submitting calls `POST /captures` with the exact typed text (`source_type: "typed"`), clears the input immediately, and shows an inline card for that capture polling `GET /captures/{id}` (roughly every 1.5s) until its `processing.state` leaves `pending`/`processing`. A background processor (`processor/runner.py`, run separately — see [local-models.md](local-models.md) — not invoked from the browser) claims the capture, sends the text plus available categories/projects/folders to local Ollama `qwen3.5:4b`, and submits one atomic interpretation; project/folder placement uses the same canonical IDs and containment semantics as manual `/move`. On `resolved`, the card disappears, the parent task list is revalidated (the new task appears through the normal `GET /tasks` list, already reflecting its parsed title/deadline/placement — reviewing/editing it uses the existing task detail panel, not a separate confirmation step), and a toast confirms. On `failed`, the card stays with the original text, the failure reason, a Retry button (`POST /captures/{id}/retry`), and an "add manually" link to `/tasks/new?raw=...&captureId=...&captureVersion=...&captureGeneration=...`, which applies a direct structured `"create"` interpretation operation against that same capture — one atomic write, no duplicate item, capture still marked resolved and fencing any later stale automated attempt. `/tasks/new` without those query parameters remains the plain manual-structured-add path (`POST /items` directly, category only, no fabricated capture), per the "user must retain a straightforward manual structured-add path" requirement.

Click a row to open a right-side detail panel with title, notes, optional due date/time, category/project, source/history access, complete/reopen, and archive. Show the due field consistently with the API's single-deadline semantics. Selecting a project supplies project context and category; extra associations remain explicit.

Completion updates the same item everywhere. If using optimistic UI, restore the previous state and show a retryable error on failure. A brief Undo can reopen the task through the API. Do not present success before a mutation is acknowledged unless its pending state is clear.

Acceptance: add an undated task, add a dated task using free text, verify locally parsed title/deadline/destination and preserved original input, correct a parsed field manually, change deadline, complete/reopen, and see matching state in the project page. Verify task ordering, refresh persistence, failed-parse recovery, and that stale parsing cannot overwrite a manual edit.

## Capture and processing feedback

Keep “Talk or type…” available on main working screens. Provide actual text input, a visible microphone control, attachment/link controls, and a submit action. Page context can be sent as a hint, not a forced destination overriding explicit user intent.

Implement typed capture first. Only enable recording and attachments when their actual backend paths exist. Keep input intact on save failure.

Distinguish these states in ordinary language:

- Saving/uploading: not durable yet.
- Saved: original persisted; waiting for interpretation.
- Organized: show actual created/updated items with View and Undo.
- Needs your input: open the relevant Inbox item.
- Processing failed: original is safe; Retry available when a processor exists.

The capture processor uses local Whisper followed by Qwen3.5-4B; typed text skips Whisper. Show Transcribing and Organizing as appropriate, then the actual result. Codex/Claude Code need not be open. If models are stopped or not yet connected, say “Saved — awaiting processing” and retain manual organization controls. Never label a reminder as scheduled merely because its text or date was stored.

## Inbox and Other

Show original text/description, source type, capture time, and a preview or playback link when available. Processing captures and extracted Inbox items need distinguishable states and must not produce duplicate cards for the same resolved result.

Suggestions show both action and destination: “Create task: Email Sarah · Due Friday · Project: Apartment Move.” Also provide Move to for choosing a category/project manually and a way to edit missing context. Preserve unresolved deadlines rather than treating every capture as just a note.

Untouched unclassified items move to Other after the chosen interval. Until configured, no automatic move is implied. Other remains searchable with the same detail and Move to actions. Processing errors do not disappear into Other. Show automatic movement in history and support backend undo.

## Categories, projects, and content

Start with a consistent item list/detail pattern instead of building six unrelated applications. Default filters may vary by category. Books can show book entities and linked notes; Learning can group notes by topic. Represent groupings without implying files must live on disk or introducing deep mandatory folders.

Projects list actual project items; a project's detail page includes its linked tasks and references. Archiving a project must explain that related tasks remain available; do not visually suggest a cascading deletion.

Recipes, food logs/calorie totals, goal progress, and reading-status interactions get dedicated fields/screens when their backend definitions are ready. Basic note storage inside Health & Food is not complete calorie tracking. Design those follow-up screens using the same shell, after the first slice works.

## Editing, sources, and history

Use readable content editing with Markdown-compatible persistence. Show Saving, Saved, or Save failed based on actual responses. Preserve local edits on failure or version conflict; offer reload/review instead of silently overwriting newer content.

Sources open the original capture, including original audio/assets when available. History shows user, MCP, processor, and automatic-routing actions with before/after context. Undo uses the backend action ID and reports conflicts clearly.

Provide a Details panel showing filename/type/size, capture time, upload time, original file timestamps when known, source app/URL, and item last-edited time. Label these separately, render timezone clearly, and show missing values as unknown. Let users correct descriptive metadata with history; do not expose observed byte size/checksum as editable facts. Do not label upload time as the date the source was created.

## Archive and permanent deletion

Archive has separate item/capture filters. Restore keeps the same ID and completion state. A completed task is found in Completed without needing to archive it.

Permanent deletion is available only in Archive, with confirmation identifying the object. Explain that deleting an interpreted item preserves shared originals. For captures still referenced by items, show the dependency and block deletion according to the API. Report media cleanup pending if physical removal is still retrying; do not promise backups are erased.

## Skills admin page

Implemented voice UI (see [features/voice-commands.md](features/voice-commands.md)): one shared recorder provider mounted in the root layout, a global voice panel for recording or typing a command, and a single review card shared by a top-right tray and Inbox. The panel follows `/capabilities`; the Skills entry for Voice commands does too.

Keep the page and the existing capability ideas, including voice-to-note, receipt extraction, link summaries, and weekly digest. Label each honestly as Planned, Available, or Disabled according to implementation/configuration. Planned capabilities remain visible so they are not forgotten.

Implementations can later add configuration, manual run, recent result, and failure information. Do not add scheduler or provider-management endpoints merely to populate a mockup. A static capability register is enough for the first UI.

## Loading, errors, and accessibility

Every data screen needs initial loading, empty, API unavailable, and retry states. Empty Tasks should lead to adding a task; empty Inbox should simply say there is nothing awaiting attention. Failed saves must preserve input.

Use real buttons, checkboxes, text fields, labels, keyboard focus indicators, and accessible dialog/detail-panel behavior. Restore focus after closing a panel. Verify narrow desktop windows, long titles, substantial lists, zoom, and scrolling without fixed-canvas clipping. Do not treat the mockup's contenteditable/autosaved labels as a persistence implementation.

## UI implementation order

After the core UI/backend, follow the separate [personal memory plan](personal-memory-plan.md) for About Me, memory review/detail, graph exploration, source-linked associations and manual memory controls. These are future additions, not prerequisites for the current screens.

1. Desktop shell/navigation, local API client, Tasks and task detail, shared category/project listings.
2. Typed capture, actual persistence states, Inbox manual routing, source-linked note editing.
3. Archive/restore/permanent-delete flows and revision/undo conflicts.
4. Global keyword search, Other, capture history, and Skills capability register.
5. Voice/media capture and category-specific screens as their backend behavior becomes available.

For each step, verify a real browser flow against local PostgreSQL, including reload, shared item IDs, and server errors. No Today implementation is needed. Keep the initial deliverable local; deployment is a separate later step.

Before calling a screen complete, verify its supported add/edit/organize/lifecycle actions with AI disabled. A chat prompt or MCP tool alone does not satisfy a manual UI requirement.
